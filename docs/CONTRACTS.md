# Phase 1 contract guide

## Source of truth

`packages/core/src/contracts.ts` defines TypeBox schemas and TypeScript types inferred from those schemas. `packages/core/src/validation.ts` provides `validateContract(name, value)` and cross-artifact repair prerequisites. Validation never coerces or mutates input. JSON Schema snapshots in `packages/core/schemas/` are generated by `pnpm build`; edit TypeBox definitions, never snapshots. `changespec.schema.json` occupies the v3-required location.

`packages/core/src/stages.ts` defines the public stage inputs/outputs. Each package exports typed stubs; calling one throws `NotImplementedStageError`. Core has no subsystem dependencies. All other subsystem packages depend only on core. The CLI currently parses commands and reports unavailable stages; orchestration is deferred.

## Artifact chain

All paths are owned by `packages/core/src/artifact-paths.ts`:

```text
.isotope/
  selected-specs.json
  bdg.json
  signatures/<codeVersion>/<fixturePair>/<entryPoint>.<payloadVersion>.<run>.json
  diff-report.json
  diffs/<codeVersion>/<fixturePair>/<entryPoint>.<comparisonKind>.json
  evidence-packets/<entryPoint>.<divergence>.json
  reasoning/<entryPoint>.<divergence>.<vote>.json
  verdict.json
  repair/packets/<repairId>.json
  repair/proposals/<repairId>.json
  repair/verification/<repairId>.json
  repair/verified-repair.json
  isotope-report.json
```

Dynamic identifiers are encoded and traversal/separators are rejected. The code-version and fixture-pair directories prevent original/patched or planning/held-out runs overwriting each other. `comparison(...)` reserves distinct original/baseline/secondary comparison artifacts for multi-entry-point and repair runs. `diff-report.json` remains the canonical single-comparison location. The final report references all comparisons. Deterministic candidates may skip proposals per v3, but their full candidate is retained with any verified repair.

`writeJsonArtifact(root, path, contractName, value)` and `readJsonArtifact(root, path, contractName)` validate typed JSON. Pass `artifactPaths(projectRoot).root` as the artifact root. `ensureArtifactDirectories(projectRoot)` creates the hierarchy. Paths must be physical (no symlink components); use a canonical project path. Helpers reject lexical escape and symlink components. They are local runner helpers, not a defense against a concurrent adversary replacing directories during an operation.

JSON output is UTF-8, recursively key-sorted, two-space indented, and newline-terminated. Arrays retain order. Non-JSON input is rejected rather than silently dropped. This is artifact serialization only: the v3 handler serializer for undefined/NaN/Date/Buffer/cycles remains a later harness implementation.

## Decisions and v3 ambiguities

- **Unspecified envelopes:** v3 gives partial examples, not full schemas for BDG, selection, reports, or verification. Phase 1 adds `schemaVersion: 1`, explicit IDs/references, and structured verification records. `VerdictReport` aggregates per-entry-point `VerdictResult` records. `IsotopeReport` retains candidate/verification references and audit hashes/raw-response references.
- **ChangeSpec drafts:** `ChangeSpec` permits `verified_by: draft` for the offline drafting output. `SelectedSpecs` requires human verification and a verification date. Repair prerequisite validation requires a distinct held-out pair when repair is enabled. No selector is implemented.
- **Config:** the schema models normalized, explicit settings; no YAML loader or implicit defaults are implemented. `repair.verify` is always literal `true`, including when mode is off, following v3 §4’s stronger rule. Limits are one primary attempt, at most three files, and at most 80 changed lines. A later mechanical retry is not an extra primary attempt.
- **Vocabulary:** serialized ChangeSpec fields retain the spec’s snake_case. Runtime artifacts use its camelCase. Canonical semantic tier is `semantic_question` from §3.5’s JSON example. Canonical configured adapter is `express_route` from §4; the prose’s `express` describes that adapter. Candidate origins are `deterministic` and `model`.
- **Non-candidate responses:** `human_decision_required` and `no_safe_repair` use `patch: null`. A repair candidate requires nonempty anchored edits. Replacement text can be empty to express a deletion; application, allow-lists, anchor uniqueness, and line-budget enforcement remain later work.
- **L6 placement:** pure verdict-resolution interfaces/stubs live in core as §2.5 specifies. There is no business logic or orchestration there.
- **CLI exit status:** help returns 0, malformed arguments return 10, and unimplemented commands return scaffold-only code 12. No stub returns a product verdict or pretends a harness ran. v3 product exit-code resolution is deferred.

## Verification boundaries

`RepairVerification` distinguishes planning and held-out evidence and all seven outcomes. Successful records require passing verdicts, baseline equivalence, stability, and all structural checks. Original baselines and patched signature references are explicitly recorded. Runtime relational validation additionally checks repair IDs, fixture IDs, distinct held-out pairs, and self-comparison run indices. `VerifiedRepair` can contain only an eligible candidate and a successful verification, and is always `offeredOnly: true`. Schema acceptance validates the shape of recorded evidence; it is not proof that execution actually happened. Only the future L10 implementation may produce real verification results.

The repair packet intentionally has no held-out field. Its builder must later enforce v3’s stronger exclusion of held-out payloads, signatures, and identifiers from every string/fragment; a shape schema alone cannot establish information provenance. Packet line/token budgets, policy predicates, verdict authority, and post-patch structural checks are interfaces/recorded constraints here, not implementations.

## Phase 1 audit

All v3 L0–L12 locations are reserved; package dependencies are acyclic. All seven verdicts, mechanical/reasoned/unavailable provenance, both proposal origins, planning/held-out pairs, original/patched code versions, and every repair outcome are representable. Candidate patches remain non-authoritative. JSON Schema snapshots and runtime tests cover all 27 registered contracts, with additional compile-time literal-union checks. No provider SDK, AST parser, model SDK, GitHub client, execution harness, patch application, or autonomous Git operation is included.

## Phase 2 handoff

Start with `RunHarness`/`HarnessInput`/`HarnessResult` in `packages/core/src/stages.ts`, implement `packages/harness-ts/src/index.ts` for one hardcoded handler, and use `SignatureSchema` plus the core artifact helpers. Obtain real provider-produced old/new payloads separately; synthetic contract examples must never be copied into product fixture directories. Run old twice and new twice; normalize only runtime nondeterminism under the v3 protocol. Then implement the minimum `diffSignatures` mechanical comparison for one FAIL and one PASS, with models and repair disabled. Phase 2 has not been started.
